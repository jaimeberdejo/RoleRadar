**Approach: single-stage build usando la imagen oficial de uv.**

Usar `ghcr.io/astral-sh/uv:python3.13-bookworm-slim` como base. Esta imagen ya trae
Python 3.13 + uv instalados, evita un layer extra de instalación de uv y es mantenida
por Astral. Es la forma canónica recomendada para producción.

**Dockerfile — pasos en orden:**

1. `FROM ghcr.io/astral-sh/uv:python3.13-bookworm-slim`
2. `WORKDIR /app`
3. Copiar solo los ficheros de dependencias primero (para cache de layers):
   `COPY pyproject.toml uv.lock ./`
4. Instalar dependencias sin dev: `RUN uv sync --frozen --no-dev`
   - Esto instala en el venv gestionado por uv dentro de /app/.venv
5. Copiar el resto del código: `COPY app/ ./app/` y `COPY data/ ./data/` (para
   profile.yaml; la DB no se copia, viene del volumen)
6. Exponer puerto: `EXPOSE 8000`
7. Variable de entorno para HF cache explícita:
   `ENV HF_HOME=/app/.cache/huggingface`
   Esto permite montar el volumen en una ruta conocida sin depender de $HOME del
   contenedor (que varía con el usuario).
8. Comando de arranque:
   `CMD ["uv", "run", "uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000"]`
   - `--host 0.0.0.0` es crítico: sin esto el servicio solo es accesible desde dentro
     del contenedor.
   - Sin `--reload` en prod (reload requiere watchfiles y es para dev local).

**IMPORTANTE — secrets:**
- NUNCA añadir `COPY .env ./` ni `ARG OPENAI_API_KEY`.
- La clave se inyecta en runtime vía docker-compose env_file (ver Task 2).
- El Dockerfile no tiene ninguna referencia a OPENAI_API_KEY ni a RapidAPI/JSearch.

**BGE-M3 — decisión (documenta en comentario en el propio Dockerfile):**
- NO se pre-descarga el modelo en build time (opción alternativa habría sido un
  `RUN python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('BAAI/bge-m3')"`,
  pero añadiría ~2.3GB a la imagen y requeriría red en build).
- En cambio, el modelo se descarga en el primer `/jobs/process` call al volumen
  HF_HOME=/app/.cache/huggingface, que se persiste con un named volume en compose.
- Documentar esto con un comentario `# NOTE: BGE-M3 (~2.3 GB) se descarga en la
  primera llamada a /jobs/process. Montar volumen hf_cache en /app/.cache/huggingface.`

Crear `docker-compose.yml` con un único servicio `buscadordeempleo`.

**Estructura completa:**

```yaml
services:
  buscadordeempleo:
    build: .
    image: buscadordeempleo:latest
    ports:
      - "8000:8000"
    env_file:
      - .env
    environment:
      # HF_HOME ya se define en el Dockerfile; lo repetimos aquí para claridad
      # y para que pueda sobreescribirse desde el shell sin rebuild.
      HF_HOME: /app/.cache/huggingface
      # La ruta de la DB dentro del contenedor, apuntando al volumen montado.
      SQLITE_DB_PATH: /app/data/jobs.db
    volumes:
      # Persistencia SQLite: la DB sobrevive reinicios y recreaciones del contenedor.
      - data:/app/data
      # Cache del modelo BGE-M3: evita re-descargar ~2.3 GB en cada restart.
      - hf_cache:/app/.cache/huggingface
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s  # BGE-M3 puede tardar en cargar en la primera llamada
    restart: unless-stopped

volumes:
  data:
    driver: local
  hf_cache:
    driver: local
```

**Decisiones de diseño a documentar en comentarios del propio fichero:**

1. `env_file: .env` — OPENAI_API_KEY se inyecta desde el fichero local. El .env
   NUNCA se copia en la imagen (ver .dockerignore). Si .env no existe, compose falla
   con un error claro antes de arrancar.

2. `SQLITE_DB_PATH: /app/data/jobs.db` — sobrescribe el default relativo del código
   para que apunte al volumen montado. Sin esto, la DB se escribiría dentro del
   contenedor y se perdería al recrearlo.

3. `start_period: 60s` en healthcheck — en la primera llamada real a /jobs/process,
   el modelo BGE-M3 puede tardar entre 30-120s en descargarse. El healthcheck cubre
   solo /health (que responde de inmediato), así que 60s es conservador pero seguro.

4. Volúmenes named (no bind mounts) — permiten que Docker gestione la ruta en el host.
   Si el usuario quiere inspeccionar la DB, puede hacer `docker volume inspect`.

5. NO incluir ninguna variable de n8n/RapidAPI/JSearch. Esas keys viven en n8n, que
   llama a las APIs de empleo por su cuenta. Este servicio nunca llama a JSearch.

6. La key de n8n (si existe) pertenece a la instancia n8n, no a este servicio.
   Añadir un comentario explícito:
   `# NOTA DE SEGURIDAD: RAPIDAPI_KEY / JSEARCH_KEY no van aquí.`
   `# Esas claves pertenecen a n8n, que llama a las APIs de empleo directamente.`
   `# Este servicio solo recibe las ofertas ya obtenidas por n8n vía POST /jobs/process.`
  </action>

## Despliegue (Docker)

Esta sección cubre el despliegue del servicio con Docker + Compose. Para desarrollo
local sin Docker, ver [Arrancar el servicio](#arrancar-el-servicio).

### Requisitos previos

- Docker >= 24 y Docker Compose v2 (`docker compose` sin guión).
- Un fichero `.env` con `OPENAI_API_KEY` (ver [Configuración .env](#configuración-env)).

### Build y arranque

```bash
docker compose up --build
```

La primera vez tarda más porque:
1. Se construye la imagen (instala todas las dependencias con uv, ~1-2 min).
2. En la primera llamada a `/jobs/process`, el modelo BGE-M3 (~2.3 GB) se descarga
   desde HuggingFace y se guarda en el volumen `hf_cache`. Las llamadas siguientes
   usan la caché y son inmediatas.

Para arrancar en background:

```bash
docker compose up --build -d
```

### Secretos y variables de entorno

| Variable | Dónde va | Obligatoria |
|---|---|---|
| `OPENAI_API_KEY` | `.env` (inyectado en este servicio) | **Sí** |
| `OPENAI_MODEL_CV` | `.env` (opcional) | No |
| `OPENAI_MODEL_SCORING` | `.env` (opcional) | No |
| `SQLITE_DB_PATH` | ya configurado en `docker-compose.yml` | — |

> **AVISO DE SEGURIDAD:** La clave de RapidAPI / JSearch (`RAPIDAPI_KEY`) y cualquier
> credencial de n8n **NO van en este repositorio ni en la imagen Docker**. Esas claves
> pertenecen a n8n, que llama directamente a las APIs de empleo (Arbeitnow, JSearch,
> FlyByAPIs). Este servicio solo recibe las ofertas que n8n ya ha obtenido, vía
> `POST /jobs/process`. Mantenerlas separadas evita filtrar la clave si la imagen
> se publica o comparte.

### Persistencia

Los datos sobreviven a `docker compose restart` gracias a dos named volumes:

| Volumen | Punto de montaje | Qué contiene |
|---|---|---|
| `data` | `/app/data` | SQLite (`jobs.db`) + perfil (`profile.yaml`) |
| `hf_cache` | `/app/.cache/huggingface` | Modelo BGE-M3 (~2.3 GB, descargado la primera vez) |

Para inspeccionar o hacer backup de la DB:

```bash
docker volume inspect buscadordeempleo_data
# La ruta real en el host aparece en "Mountpoint"
```

### Healthcheck

El servicio declara un healthcheck sobre `GET /health`. Verificar el estado:

```bash
docker compose ps
# Estado debe ser "healthy" (puede tardar ~30s en marcar healthy la primera vez)
```

### Cómo n8n alcanza el servicio

**Desarrollo local (n8n también en Docker):**

Si n8n corre en Docker en la misma máquina:
- Mac/Windows: usar `http://host.docker.internal:8000` como base URL en los HTTP
  Request nodes de n8n.
- Linux: usar la IP del host (`ip addr show docker0 | grep inet`) o añadir
  `buscadordeempleo` a la red de n8n con `networks` en compose.

**Producción:**

Desplegar el servicio en un host accesible (VPS, Railway, Fly.io, etc.) y configurar
las URLs de los HTTP Request nodes de n8n con el dominio público, por ejemplo
`https://buscador.tudominio.com`. Para autenticación, añadir un reverse proxy
(Nginx/Caddy) con API Key o Basic Auth (fuera del scope de este proyecto).

Ver la sección [Integración con n8n](#integración-con-n8n) para el contrato JSON
completo de los endpoints.
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host → imagen Docker | Env vars del host (OPENAI_API_KEY) cruzan al contenedor vía env_file |
| imagen → HuggingFace | El contenedor hace peticiones salientes para descargar BGE-M3 en la primera ejecución |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-docker-01 | Information Disclosure | Dockerfile COPY / imagen | mitigate | .dockerignore excluye .env explícitamente; sin ARG/ENV con secrets; imagen no contiene credenciales |
| T-docker-02 | Information Disclosure | docker-compose.yml en repositorio | mitigate | env_file apunta a .env local (gitignored); ninguna clave baked en el compose; comentario explícito sobre RAPIDAPI_KEY |
| T-docker-03 | Tampering | Volumen hf_cache compartido | accept | El modelo se descarga de HuggingFace oficial; riesgo bajo en uso personal local; mitigación completa requeriría digest pinning del modelo |
| T-docker-04 | Denial of Service | BGE-M3 descarga bloqueando healthcheck | mitigate | start_period: 60s en healthcheck; /health responde inmediatamente sin cargar el modelo |
</threat_model>
